# Requirements Engineering Standard

## 1. Обязательная процедура
До реализации новой функции или фазы активируется `requirements-engineer`.
Он изучает `AGENTS.md`, Master TZ, Roadmap, ADR, Decision Register и фактическое состояние
репозитория. Требования не формируются только по названию задачи.

## 2. Качество требования
Каждое требование должно быть атомарным, однозначным, необходимым, реализуемым и проверяемым.
Слова «быстро», «удобно», «современно», «надёжно» без измеримой метрики запрещены в нормативных
требованиях. Если порог неизвестен, указать `TBD — benchmark required`, а не придумывать число.

## 3. Обязательные поля
ID; название; формулировка SHALL; rationale; приоритет; источник/статус решения; входы/выходы;
единицы/CRS/форматы; ошибки и восстановление; offline/network dependencies; метод проверки;
Given/When/Then; связанные модули; статус реализации; evidence.

## 4. Приоритеты
P0 — блокирует базовый сценарий или целостность данных.
P1 — необходимо для Version 1.0.
P2 — полезное последующее развитие.
P3 — необязательное расширение.

## 5. Acceptance
Для каждого P0/P1 требования нужен тест или явно описанная ручная процедура. Тест должен проверять
ожидаемое поведение, а не только отсутствие исключения. Для пространственных данных учитываются
CRS, transform, nodata, resolution, extent, dtype и единицы, когда они влияют на результат.

## 6. Изменения
Изменение требования требует обновить его ID/версию, трассировку, документацию, ADR при необходимости,
миграции и тесты. Исторические ID не переиспользуются.
