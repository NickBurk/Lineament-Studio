# New Repository Baseline

## Статус
`Lineament-Studio` — новый GitHub-репозиторий, создаваемый с нуля.

## Источник требований
Единственная исходная нормативная база — Master Specification, документы `00_PROJECT`–`12_PROJECT_CONTROL`,
принятые ADR, Decision Register и последующие явные решения пользователя.

## Что переносится
- согласованные продуктовые цели и ограничения;
- требования и критерии приёмки;
- целевая архитектура и контракты;
- спецификации DEM, детекторов, LSM и структурного анализа;
- модель проекта `project.lspx`;
- правила экспертной разметки и датасетов;
- исходные файлы Engineering Skills Pack v1.0;
- QA, Code Review, Git и Release procedures.

## Что НЕ переносится
- исходный код и бинарные файлы из `linia-app`;
- ветки, commits, tags, pull requests и Git history старого репозитория;
- старые тесты и сборки;
- старые project files и runtime artifacts как часть нового baseline;
- старые дефекты как подтверждённые свойства нового кода.

Сведения о старых дефектах не должны становиться требованиями к реализации без отдельного подтверждения.
Например, повторное открытие DEM остаётся обязательным новым acceptance scenario по требованиям
надёжности проекта, но не трактуется как перенос старого bugfix или старого кода.

## Совместимость данных
Целевой формат нового проекта — `project.lspx` согласно ADR-0001.
Импорт данных из иных/старых форматов не входит автоматически в scope. Если пользователю потребуется
импорт ранее созданных пользовательских проектов, это оформляется отдельным требованием и отдельным
migration/import design. Это не является переносом исходного кода.

## Первый этап
Вместо аудита старого репозитория выполняется `Phase 0 — Repository Bootstrap & Architecture Baseline`:
1. Проверить, что репозиторий действительно пустой или содержит только явно созданные стартовые файлы.
2. Разместить Master Specification и Skills в корне репозитория.
3. Устранить противоречия между файлами документации.
4. Проверить, что Codex видит корневой `AGENTS.md` и repo-local Skills.
5. Сформировать минимальный repository skeleton и правила разработки.
6. Подготовить ADR по открытым техническим решениям.
7. Создать baseline commit/PR только после проверки пользователем.
