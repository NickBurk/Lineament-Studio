# ADR-0002 — Привязка JSON/JSONL и жизненный цикл задания

- Статус: Proposed
- Дата: 2026-11-27
- Авторы: Phase 0 Architecture
- Связанные требования: NFR-COMP-001/002, NFR-REL-001/002, NFR-SEC-001, AC-JOB-001, BAT-001. Вопросы OQ-21–24.

## Контекст

DEC-A03/A04 и API Contracts определяют отдельный Worker, JSON job manifest и поток JSONL events. Не определены привязка к каналам, проверка совместимости, доставка cancel и правила сопоставления terminal event с exit code. Desktop и QGIS нуждаются в одинаковой семантике. [API Contracts](../../../02_ARCHITECTURE/API_CONTRACTS.md)

## Решение к согласованию

- Один дочерний процесс на активное задание для первого вертикального сценария. Последовательный batch использует тот же контракт и повторяет запуск с новыми job IDs. В дальнейшем нагрузка определит необходимость пула.
- Версионированный preflight вызов Worker сообщает поддерживаемый диапазон протокола до запуска задания. Клиент запускает доверенный executable по argv с отключённой shell-интерпретацией.
- Первый UTF-8 JSON record в stdin содержит job manifest. Следующий допустимый управляющий record — `cancel` с тем же job ID и версией. Один объект на строку и ограничение размера записи. Worker пишет только JSONL events в stdout. Диагностика поступает в stderr. Клиент независимо дренирует оба потока.
- Переходами задания владеет Job Manager в Core. Lifecycle включает валидацию, выполнение и ровно одно terminal состояние на принятое задание. `cancel_requested` обозначает подтверждение получения, финальное `cancelled` наступает на безопасной границе. Повторная отмена идемпотентна. Начатая финальная фиксация результата доходит до завершения или recovery.
- Клиент завершает наблюдение после terminal event и подтверждения выхода. EOF, обрыв, malformed events, неоправданная смена job ID и exit code, противоречащий исходу, имеют отдельную диагностику transport failure. Источник факта публикации после сбоя — status/artifacts каталога, когда появится persistence. Повтор по умолчанию получает новый UUID и не перезаписывает опубликованные результаты.
- До принятия зафиксировать таблицу событий, required payload, UTC timestamp, validation/error codes, правила minor/unknown fields, значения exit codes, framing limits и безопасное закрытие активной задачи. Явно проверить поведение при гонке cancel/completed.

## Рассмотренные альтернативы

File-based JSON request + JSONL event file упрощает сохранение wire evidence, но требует lifecycle протокола для временных файлов, polling и специального канала отмены. Долгоживущий процесс уменьшает startup overhead и требует дополнительной изоляции ошибок, идентификации сессии и управления ресурсами. HTTP/socket переносит границу за пределы текущего решения о локальном IPC и добавляет отдельный lifecycle и security surface.

## Последствия и риски

Минимальный headless contract harness сможет проверять обе стороны по одним fixtures. Цена подхода — startup latency на каждое задание и процессное управление на Windows. Ограничения строк, дренирование stderr, завершение после таймаута и очистка дочерних процессов влияют на устойчивость при сбое.

## Миграции и совместимость

Фиксируется первая версия контракта. Контракт выпускается после тестов совместимости на документации и JSON fixtures. Неподдерживаемая major version сообщает стабильную ошибку до запуска операции. Решения о minor, unknown fields и retry фиксируются вместе со схемами.

## Проверка корректности

Позитивный и негативный обмен; mismatched version; invalid JSON; duplicate job ID; reordered events; UTF-8; oversized frame; stderr burst; cooperative cancel; crash/EOF; race отмены и terminal event; перезапуск. Phase 1 использует тестовый subprocess с fixture events, интеграция приложения проводится после появления Worker.
