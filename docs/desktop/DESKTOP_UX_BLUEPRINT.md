# Desktop UX Blueprint — первый вертикальный сценарий

**Статус:** проект UX для review и прототипирования; это не описание уже реализованного Desktop.  
**Владелец:** Agent04 (Desktop UI/UX).  
**Основание:** UI-001–004, `05_INTERFACE/*`, Desktop Architecture, API Contracts, Project Storage и DEM Processing.  
**Границы:** структура окон, состояния и поведение. Не добавляет Core API, IPC, форматы данных, зависимости и архитектурные решения. Любой вариант поведения, помеченный «предложение», требует подтверждения владельца соответствующего контракта перед реализацией.

## 1. Пользовательская цель и принципы

Пользователь должен ответить на четыре вопроса без знания внутренней архитектуры: какой проект открыт, какие данные доступны, что сейчас происходит и как восстановиться после проблемы с источником. Главная рабочая область — карта; технические метаданные доступны рядом с данными и не прячутся за цветом или пиктограммами.

- Основное: проект, данные, карта, текущий контекст.
- Вторичное: навигация, инспектор, очередь задач; эти панели можно сворачивать.
- Рискованные действия (Copy, замена пути с другой checksum, удаление слоя, отмена/закрытие с задачей) объясняются до подтверждения.
- Ошибка содержит: что не удалось, затронутые данные, безопасное следующее действие, диагностический код при наличии. Не выводить сырой traceback как единственное сообщение.
- Проект offline-first. Недоступный сетевой источник не блокирует открытие проекта и просмотр доступных локальных данных.

### Области и размеры (предложение для прототипа)

Для базового окна 1440×900 logical px: верхняя строка 48 px; левый rail 200 px; правая контекстная панель 300 px; нижняя полоса 32 px в свернутом состоянии и до 240 px при раскрытии. Это начальные точки, а не обязательные ограничения. При изменении размера центральная область получает или теряет ширину первой. На 1280×800 панели остаются доступны, карта сохраняет не менее 55% ширины содержательной области. При меньшей ширине rail и инспектор сворачиваются в панели с явным названием и горячей клавишей; основной сценарий не должен требовать горизонтального скролла.

| Область | Содержимое и правила |
|---|---|
| Верхняя панель | Имя проекта и маркер несохранённых изменений; Save; Add data; Run только при применимых выбранных данных и валидных параметрах; меню проекта: New/Open/Close. Иконка всегда имеет подпись или tooltip. |
| Левый rail | Фиксированная навигация рабочих пространств из `WORKSPACES.md`; показывает активный проект и число задач/предупреждений текстом или бейджем. Disabled workspace сопровождается причиной. |
| Центральная область | В Data Workspace — карта и/или таблица слоёв с переключателем вида. В не-картографических рабочих пространствах — соответствующий контент; карта может оставаться общей, только если это не создаёт второй источник состояния. Выбор слоя синхронен с инспектором. |
| Правая панель | Контекст выбранного слоя/объекта/параметра. Сворачиваемая. Закрытие не сбрасывает выбор. В Data показывает provenance и полные метаданные; в параметрах — контекстную справку. |
| Нижняя панель | Сводка активных/ожидающих задач, предупреждений и логов. Раскрытие по вкладкам. Счетчик предупреждений открывает список; переход к записи фокусирует связанный слой/задачу. |

Настройки видимости панелей являются предпочтением интерфейса пользователя. Размер центрального canvas всегда приоритетен; состояние панелей не меняет данные проекта. При смене workspace сохраняются разумные размеры; контекстная панель обновляет содержимое, но не теряет selection проекта. Закрытие/сворачивание нижней панели не прекращает задания.

## 3. Навигация и действия

Порядок workspace соответствует рабочему циклу, существующий список из `WORKSPACES.md` является нормативным именованием. Dashboard — сводка и вход в проект; Data — источники и слои; Detection/LSM/Structural — анализ; Review/Dataset — экспертная работа; Smart Workflow — компактные рекомендации; Reports — публикация результатов; Settings — профили и runtime. Глобальные команды New/Open/Close/Save доступны независимо от workspace. Действия конкретного слоя находятся в контекстной панели или меню слоя, а не в дублирующих toolbar-кнопках.

`Run` не является фиктивным универсальным действием: оно предлагает только операции, реально доступные в текущем состоянии приложения. До поставки соответствующего use case элемент не показывается как активная кнопка. Разделение этого blueprint и реализации является явным: спецификация не означает наличие функций.

## 4. Map Canvas prototype — будущая спецификация

Цель прототипа OQ-01/OQ-29 — проверить карту на целевом ноутбуке, прежде чем распространять canvas на все рабочие пространства. Поддерживаемый срез: GeoTIFF raster (windowed reads и доступные overviews), GeoPackage raster/vector layers, несколько слоёв, visibility/order/opacity, выбор объекта/линии, отображение CRS и явное преобразование к CRS вида, Overlay (default для сравнения), Swipe и Side-by-side. Экспорт/редактирование геометрии в этот срез не подразумевается сверх уже заданной архитектурой поддержки базового выбора и редактирования; границы редактирования должны пройти отдельный scope review.

- Векторные линии выбираются hit-test-ом с толерантностью в экранных пикселях; выбор открывает атрибуты/идентификатор в инспекторе. Не менять исходную геометрию при выборе.
- CRS трансформация выполняется в слое отображения с видимым указанием исходного и canvas CRS; неизвестный/отсутствующий CRS не угадывать, такой слой получает понятное предупреждение и не участвует в географически корректном overlay до решения пользователя.
- Raster reads ограничены видимым extent и уровнем масштаба; не читать весь растр при первом показе. Кэш ограничен и сбрасываем. Данные вне окна остаются доступны для последующей подгрузки.
- Opacity имеет подпись и числовое значение; Overlay показывает легенду/порядок; Swipe — draggable divider и клавиатурно доступная настройка положения; Side-by-side явно подписывает каждую панель и синхронизирует extent по умолчанию.
- Отключение/ошибка одного слоя не ломает остальные. NoData прозрачен, если корректно описан источником; интерпретация маски остаётся видимой в свойствах.

### Предлагаемый план benchmark для OQ-01/OQ-29

Провести на чистой Windows-сборке будущего прототипа; повторить по 10 раз после одного холодного запуска и после 3 повторных открытий. Измерять p50/p95 wall-clock, peak RSS процесса UI и worker отдельно, ошибки чтения/рендера и стабильность файловых handles. Данные: 1k×1k, 5k×5k, 10k×10k, 20k×20k GeoTIFF; как минимум два CRS; один rotated transform и NoData fixture; 1, затем 5 GeoPackage слоёв (растровые/векторные). Для 16 GiB RAM, integrated graphics, Standard profile:

| Метрика | Предлагаемый UX acceptance threshold |
|---|---|
| Показ первого корректного viewport для 1k/5k | p95 ≤ 2.0 s / ≤ 3.0 s соответственно |
| Перемещение/zoom по уже открытому viewport с тёплым cache | p95 ≤ 150 ms на кадр; UI event loop не блокируется дольше 100 ms |
| Первый viewport 10k/20k с windowed read/overviews | p95 ≤ 5 s / ≤ 8 s; загружается видимый extent, не вся сетка |
| Переключение Overlay/Swipe/Side-by-side для 5 слоёв | p95 ≤ 1.0 s после готовности источников |
| Peak RSS UI процесса без вычисления | ≤ 1.5 GiB; общий прирост cache после 20 минут панорамирования ограничен ≤ 512 MiB и возвращается после очистки |
| Открытие/reopen того же проекта и DEM | второй/последующие reopen p95 ≤ 3 s (1k/5k), ≤ 8 s (20k) при доступном источнике; повторный open не накапливает >10% RSS на прогон после прогрева |
| Стабильность | 100 последовательных операций pan/zoom/visibility/switch mode без crash, зависания >2 s, незакрытых растровых handles или потери проекта |

Это **предлагаемые стартовые пороги для эксперимента**, не факт производительности и не утверждённый NFR. Если данные репрезентативны, а пороги неприемлемы, Desktop/GIS/QA должны предложить изменение OQ-01/OQ-29 и получить решение. Инструментировать latency отдельно по file open, metadata, overview/window read, reprojection и paint; иначе результат не позволяет найти узкое место.

## 5. Сквозные UX критерии

- UI-001: в каждом workspace доступны глобальные действия и название проекта; переход не теряет selection/проект.
- UI-002: активный параметр открывает контекстную карточку со стабильным ID, назначением, единицами, диапазоном, default, validation, влиянием изменения, взаимодействиями и ссылкой на научное объяснение.
- UI-003: сравнимые previews используют одну область, масштаб и контраст; демонстрационный preview явно обозначен.
- UI-004: каждый применимый экран/операция имеет состояния из matrix в `ACCESSIBILITY_AND_STATE_MATRIX.md`; переходы и доступные действия определены.
- PROJ-001..004 / DATA-001..009: сценарии открытия, preflight, повторного открытия, отсутствующего источника и CRS описаны в `DATA_WORKSPACE_VERTICAL_SLICE.md`.

## 6. Границы и открытые вопросы

Этот blueprint не принимает решение о новом API и не определяет storage/job state поверх утверждённых файлов. Закрытие приложения при активной задаче требует явной UX-политики, использующей существующий Core lifecycle; см. вертикальный срез. OQ-01/OQ-29 остаются OPEN до прототипа и собранных измерений. Карта не реализуется этим документом.
